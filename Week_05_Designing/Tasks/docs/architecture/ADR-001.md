# ADR-001: Managed backend for Teamify

Status: Accepted.  
Date: 2026-10-28

## Context

Teamify needs accounts, personal tasks, teams and administrators, shared agendas and events, invitations, polls, group chat and real-time notifications (data/Teamify.txt, US1–31).

We plan a small first version and want to simplify development. User numbers, traffic, budget and availability targets have not been specified. There is no current requirement for separate backend applications.

## Decision

Use ready-made services for login, database storage, running server-side functions and real-time updates. We write Teamify's business rules and access checks. Keep the code organized by responsibility: accounts, teams, tasks/events, chat, polls and notifications.

The cloud provider has not been selected yet.

## Architecture overview

```text
[Client] -- sign in --> [Authentication service]
[Client] <-- identity token -- [Authentication service]

[Client] -- request + token --> [Server-side functions]
                               Check identity, permissions and input
                                        |
                                   read / write
                                        v
                                  [Managed database]
                                  Tasks, teams, events,
                                  messages, votes, notifications
                                        |
                                  saved changes
                                        v
[Client] <-- allowed updates -- [Real-time service]
```

The token identifies the user. It does not by itself prove membership of every team. Functions and database rules check task ownership, team membership and administrator rights. The real-time service must also check who is allowed to subscribe and remove access when membership ends. After reconnecting, the client retrieves missed messages from storage.

## Who does what

| Provider supplies and runs | We implement or configure |
| --- | --- |
| Login and password-reset service | Login integration, profiles, logout and account deletion |
| Database infrastructure | Data structure, queries, indexes and access rules |
| Function execution | Validation, team roles, task/event operations and voting rules |
| Real-time delivery | Allowed subscriptions, notification triggers and missed-message handling |

We still test the application, monitor usage and failures, and configure the services correctly.

## Alternatives and reasons

| Option | Benefit | Main drawback | Assessment |
| --- | --- | --- | --- |
| Modular monolith | One backend; easier debugging and related database updates | We run the backend; modules are released together | Suitable alternative |
| Microservices | Services can be updated and scaled separately | Network failures and keeping data and permissions consistent across services | More complexity than the first version currently needs |
| Managed/serverless backend | Ready-made capabilities and less infrastructure work | Provider dependence, service limits and usage-based costs | Preferred option |

The priority is simpler development. The student prefers ready-made services and accepts dependence on the provider for the first version. We have not measured costs or traffic, so we do not claim this is the cheapest option.

A monolith can also use a managed database or login service. Our choice is to rely mainly on ready-made backend capabilities rather than operate one custom backend or several services.

## Example: send a chat message

1. The signed-in client sends the team ID and message to a server-side function.
2. The function checks the user's identity, current team membership and message input.
3. It saves the message with a server-assigned ID and sender identity derived from the verified login.
4. The real-time service delivers the saved message to authorized connected members.
5. Members who were offline can retrieve saved messages after reconnecting.

The client cannot give itself access by changing the team ID or claiming to be an administrator.

## Example: create an event

Check that the user is a team administrator. Save the event, invitations and pending notifications together in one database transaction. Send notifications only after saving succeeds, and handle retries without creating duplicate notifications.

The chosen database must support these related updates. Sending a notification is separate from saving it and can fail independently.

## Consequences

Benefits:
- Less work running servers and implementing common login features.
- Ready-made storage and real-time delivery.

Drawbacks and remaining work:
- Moving to another provider may require rewriting integrations.
- Check limits, monitor usage and set cost alerts.
- Enforce permissions on operations and subscriptions, not just in the interface.
- Define how account deletion removes personal data and affects shared records (US7).

## Open questions and when to reconsider

Before choosing a provider, clarify expected usage, budget and reliability needs. Also clarify joining teams, notification triggers, voting rules and deletion of related records.

Reconsider the choice if measured costs, service limits, reliability or migration needs become a problem. Add separate services only when a concrete need appears.
